# Update — 2026-07-11

State of the project as of this date, written so any developer, contributor, or AI agent can pick it up with owner-level understanding: not just *what* the code does, but *why* it is shaped this way and where the traps are.

## What this project is

**قرآن — آية بآية** (Quran — Ayah by Ayah): a Chrome extension (Manifest V3) whose toolbar popup shows exactly one Quran verse at a time, with next/previous navigation, searchable surah/verse pickers, and automatic saving of the reading position. Strictly RTL, Arabic-only UI, cold green/white palette. Current version **1.0.0**, fully tested and packaged for the Chrome Web Store (`dist/one-quran-v1.0.0.zip`).

## Change history (chronological)

1. **Initial build** — MV3 popup extension, no framework, no bundler. Quran data (114 surah JSON files + index) downloaded once from [semarketir/quranjson](https://github.com/semarketir/quranjson) and bundled; position persisted via `chrome.storage.local`; searchable dropdowns; RTL layout.
2. **Inline ayah number** — the ayah number marker `﴿١٣﴾` moved from a separate element to inline at the end of the verse text (mushaf-style), styled via `.ayah-marker` span appended inside `#ayah-text`.
3. **Search modal + tashkeel-insensitive search + real font + rounded corners**:
   - Pickers changed from cramped anchored dropdowns to a **modal overlay** inside the popup (search input on top, scrollable list below, close via ✕ / backdrop / Escape / selection).
   - **`js/arabic.js`** added: normalizes both indexed text and queries so bare Arabic (no tashkeel) matches the fully-vocalized Uthmani text.
   - The exact **Amiri Quran** webfont (the v19 woff2 files Google Fonts serves to Chrome) bundled in `fonts/` — previously the CSS only *named* the font and silently fell back to Geeza Pro.
   - Rounded corners: `border-radius` on `body` made effective by clipping overflow; `html` transparent.
4. **Store readiness** — packaging script with junk-file verification, anti-aliased icons (4× supersampled), `aria-label`s on search inputs, 1280×800 store screenshots, ready-to-paste listing/privacy texts (`store/`), E2E suite committed to `test/e2e.mjs`.

## Architecture

### Runtime flow

```
popup opens
  → popup.js init()
      → data.js loadIndex()            (~30 KB surah-index.json, fetched once)
      → storage.js getPosition()       ({surah, ayah}, default 1:1)
      → render()
          → data.js loadSurah(n)       (single surah file, memoized in a Map)
          → header: surah name / آية x من y / juz number (computed from index juz ranges)
          → verse text + inline ﴿n﴾ marker
          → dropdown.js pickers rebuilt (surah picker once, verse picker per render)
          → storage.js savePosition()  (fire on every navigation)
```

No background service worker, no content scripts, no network requests at runtime — everything is popup-local. The 6,236-ayah corpus never loads at once; only the index plus the currently-read surah.

### Modules

| File | Responsibility | Owner-level notes |
|---|---|---|
| `js/popup.js` | Entry point: state (`currentSurah`/`currentAyah`), render cycle, navigation (incl. cross-surah), keyboard (← next / → prev, RTL-natural), wiring pickers | `renderVerseDropdown` **must call `verseDropdown.destroy()`** before recreating — picker overlays live on `document.body`, not in the container, and would leak one per navigation otherwise (covered by a test) |
| `js/data.js` | Lazy data access: `loadIndex()`, `loadSurah(n)` (Map-memoized), `getAyahKeys`, `getAyahText`, `getJuz` | Falls back from `chrome.runtime.getURL` to relative URLs so the popup runs as a plain web page for dev/testing. `verse_0` (bismillah, present in 112 files) is deliberately excluded from numbering |
| `js/storage.js` | `getPosition`/`savePosition` on `chrome.storage.local` | Falls back to `localStorage` outside the extension context (dev preview + E2E tests rely on this) |
| `js/dropdown.js` | `createDropdown(...)`: trigger button + modal overlay picker with optional debounced search | Search input only when `showSearch` (verse picker uses `count > 20` per the original spec); `wrapItems` gives 2-line clamped verse rows |
| `js/arabic.js` | `normalizeArabic()` for search | See "search normalization" below — the subtlest code in the repo |
| `css/popup.css` | 420×420 popup, palette, modal styles, bundled `@font-face` | `.picker-overlay[hidden] { display: none }` is **load-bearing**: the overlay's `display: flex` would otherwise defeat the `hidden` attribute (this bug shipped briefly; a computed-style test now guards it) |

### Data format (bundled in `data/`, source: quranjson)

- `surah-index.json` — array of 114: `{ index: "001", title, titleAr, count, place, type, juz: [{index, verse: {start: "verse_1", end: "verse_141"}}] }`. Juz number for the current ayah is computed by walking these ranges.
- `surah/surah_N.json` — `{ index, name, count, juz, verse: { verse_1: "...", ... } }`. Keys are `verse_<n>`; `verse_0` = bismillah decoration in all surahs except 1 and 9.
- Validated invariants: index counts == numbered verse keys everywhere; total 6,236 ayahs; every ayah falls in a juz range.

### Search normalization — why it works the way it does

The Quran text is **Uthmani script**, fully vocalized. Users type modern bare Arabic. `normalizeArabic()` (applied to BOTH the indexed text and the query):

1. Strips tashkeel/hamza marks (U+064B–065F), dagger alef (U+0670), Quranic annotation signs (U+06D6–06ED), tatweel (U+0640).
2. **Deletes every alef form (ا أ إ آ ٱ) entirely** — not "normalize to ا". Reason: Uthmani spells words like ملائكة with a *dagger alef* (stripped in step 1) where modern spelling has a real alef, so keeping alefs makes such queries unmatchable. Deleting on both sides restores matching (`الرحمن` finds `ٱلرَّحْمَٰنِ`) at the cost of some false positives — an acceptable trade for a picker filter.
3. Maps ى→ي, ة→ه, ؤ→و, ئ→ي. Arabic-Indic digits are converted to Latin separately in `dropdown.js`.

⚠️ **Bidi trap**: the regex character classes in `arabic.js` contain literal Arabic characters whose *visual* order in an editor differs from their logical order. Editing them by eye has already caused a range to accidentally swallow the digits ٠-٩ once. If you touch these regexes, verify with the digit-survival check (see tests) or rewrite using `\uXXXX` escapes.

### Build-time scripts (never run in the shipped extension)

- `scripts/fetch-data.mjs` — one-time download of the 115 JSON files from raw.githubusercontent (static host, no API limits).
- `scripts/fetch-font.mjs` — downloads the exact Amiri Quran woff2 subsets by fetching the Google Fonts CSS **with a Chrome User-Agent** (default UA gets a ttf instead).
- `scripts/make-icons.py` — dependency-free PNG writer; renders the crescent at 4× and box-downsamples for anti-aliased edges.
- `scripts/package.mjs` — builds `dist/one-quran-v<version>.zip` from the runtime allowlist and **fails the build** if any junk or `_`-prefixed path (reserved by Chrome) appears in the archive.

## Testing

`test/e2e.mjs` drives the popup in headless Chrome over the DevTools Protocol (raw WebSocket, no dependencies — Node ≥22):

```bash
# terminal 1: serve the extension dir (storage.js/data.js fall back to web APIs)
python3 -m http.server 8749 --bind 127.0.0.1
# terminal 2: headless Chrome with CDP
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new \
  --remote-debugging-port=9224 --user-data-dir=/tmp/oq-profile about:blank &
node test/e2e.mjs
```

21 checks: font actually loaded (`document.fonts.check`), modal open/close via every path, *visual* state via `getComputedStyle` (not just the `hidden` property), bare-Arabic + Arabic-digit search, two-line items, overlay-leak counting, cross-surah navigation, boundary button disabling, position persistence across reload. The same suite was run against the unzipped store package before submission. Note: the "initial ayah 1:1" check requires a fresh Chrome profile (localStorage persists per profile).

**Screenshot gotcha**: headless Chrome enforces a ~500px minimum window width; in an RTL document the 420px body then anchors *right*, which looks like a broken layout in screenshots. It isn't — use CDP `Emulation.setDeviceMetricsOverride` at exactly 420×420 (see how `store/stage.html` shots were made).
